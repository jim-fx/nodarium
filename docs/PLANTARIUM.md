# Plantarium

Plantarium is the node system in `nodes/max/plantarium`. Its nodes generate plants, with the value nodes of [Core](./CORE.md). All of them use `nodarium_utils` (`packages/utils`), which implements the formats below, so node code rarely touches them directly.

## Alpha and the path

A number input of a plant node is a plain value or an expression of the value nodes of [Core](./CORE.md) (`math`, `random`, `alpha`, `curve`, `wave`, ...), or of `path_info`, the one value node of Plantarium: `[5, field]`, a value of the path the node works on, field is the option of the node (0 position, 1 index, 2 count, 3 depth, 4 parent position, 5 length, 6 grown, 7 age). CORE.md describes the expressions and how `random` draws its values. The plant nodes tell an expression where it is read:

`branch` and `instance` set `ctx.alpha` before they evaluate the inputs of each branch or instance, for example its `length` or `size`: alpha is where it sits on its parent path. `ramify` sets it to the generation of the node whose rule it reads, see L-system. `stem` and `branch` read `thickness` with `ctx.float_along` at every point of the path they create, there alpha goes along that path. `float_along` draws random values once, so a `random` thickness stays the same along the path. The path is then multiplied by `1 - alpha * taper`: `taper` 1 (the default) makes a cone, 0 leaves the profile to the thickness input. Everywhere else alpha is 0.

Alpha is only one number that changes from place to place, so it can't tell a node about the path itself. `stem`, `branch`, `ramify`, `instance`, `gravity`, `rotate`, `noise`, `keep_apart` and `apply_force` also call `ctx.set_path` (or `ctx.set_path_info` for a stem or an axis that doesn't exist yet) before they read the inputs of each path. It sets `ctx.path`, what the `path_info` node reads: the `index` in the header of the path (the number among the paths its creator made on the same parent, it stays when other paths come or go), the place of the path among the paths the node works on (the `position`) and how many there are, its depth, where on its parent it grows (the `parent_alpha` of its link, 0 for a stem) and its length. `set_path` also sets alpha to the position of the path, from 0 at the first to 1 at the last, so `alpha` reads the same as `path_info` with position until a node sets it to something else. A `branch` or `instance` works on the path it places its branches or instances on, so a `branch` on the points of a whorl reads where the whorl sits on its stem. A `path_info` value doesn't change along a path or from one branch to the next, only from path to path.

## Path

```
[0, stem_depth, id, parent_id, parent_alpha, creator, index, grown, ...points]    each point: x, y, z, thickness
[type, stem_depth, id, parent_id, parent_alpha, creator, index, grown, ...points, ...colors?, ...fibres?, ...fill?]
```

The type says what a path carries at every point after its points, it is the sum of them (`point_values` in `nodarium_utils::geometry`, `POINT_VALUES` in `@nodarium/utils`): 16 an RGBA8 color (`COLORED_PATH`, see Colors), 32 the fibres and 64 the fill of Myzel's `hyphae_to_mesh` (f32, see Fibres and fill in [MYZEL.md](./MYZEL.md)). A plain path has the type 0. `is_path` and `wrap_path` take every type, `wrap_path` gives the points and each value apart, so a node that moves the points of a path keeps its values without knowing them. A node that makes a path anew with other points takes them along with `PointValues::at_lengths`.

The header says where the path sits in the plant, so a node, the viewer or a material can pick any part of it:

- `creator` is the id of the graph node that made the path. The host fills it into the hidden `creator` input of `stem` and `branch` (type `creator`, like `seed` it can't be wired or set), so every path of a node has the same one, `creator == X` selects everything one node made.
- `parent_id` is the `id` of the path this one grows on, `-1` for a path that has no parent. `parent_id == X` selects the children of a path, walking up the parents (`pathLineage` in `@nodarium/utils`) the descendants.
- `index` is the number of the path among the paths its creator made on the same parent, the first is 0.
- `id` is a hash of `creator`, `parent_id` and `index` (`path_id` in `nodarium_utils::geometry`, never negative). It only depends on these three, so it is the same in every run and doesn't change when other paths come or go: more stems, another amount of branches on a different path, a node somewhere else in the graph. Changing the amount of a node only adds or removes the paths with the highest indexes, a branch that is skipped leaves a gap in the indexes instead of renumbering the rest. Two paths of a list never share an id (unless the same list is joined twice, see `join`).
- `parent_alpha` is an `f32`, where along the length of the parent (0 to 1) the path is attached.
- `grown` is an `f32`, how much of the path has grown, see Growth. 1 is a full-grown path.

### Growth

A path that is still growing is the lower part of the full-grown one. `stem`, `branch` and `branch_from_points` have a hidden `growth` input: below 1 the path is that share of its `length`, above 1 it is full-grown and only gets older. They write it into `grown` of the header (`PathLink::grown`), and a node that copies a path or its link keeps it.

Places on a path are shares of its full-grown length: `parent_alpha` of a child, the alpha of a point, and `lowest_...` and `highest_...` of the nodes that place something. `PathLink::spot(alpha)` gives the place on the path as it is now, or nothing when the path has not grown that far. Everything below the tip stays where it will be on the full-grown path while the tip grows on: nothing slides up the path. `gravity` (along each path) and `noise` read alpha and the length of the full-grown path too, so the grown part keeps its shape. `follow_parents` finds the spot of a child the same way.

Growth never changes which paths a plant has, only how long they are. What lies above the tip is dormant: `points_on_path` and `trunk_kink` still give its point, it waits at the tip (a dormant kink bends nothing), `branch` and `branch_from_points` make its branch as a bud, and `instance` and `instance_from_points` place nothing there. A bud is a path with `grown` 0 (`PathLink::is_bud`): it has its id, its link and its layer, is `BUD_LENGTH` long and is not drawn by `output` and `to_geometry`. A branch whose own `growth` is 0 is a bud too. So the layers, the ids, the indexes, the counts of `path_info` and the random values are the same at every time, and a node that works on the deepest layer finds the branches there before the first of them has started.

`path_info` reads the growth of the path a node works on as `grown`, and as `age`: `grown` minus alpha, how long ago the tip grew past the spot. It is 0 where the tip is now and rises as the path grows on, also after the path is full-grown, as long as its `growth` rises above 1. An age into the `growth` of a branch or the `size` of an instance starts it when the tip of its parent reaches it, without a jump. The growth of a branch is the `grown` of the path its own leaves and twigs read, so one `time` into the `growth` of the stems drives the whole plant, level by level. The thickness of a `stem` or branch reads alpha along the path as it is now, so the tip stays closed while it grows.

To let what is already there move up a little, like internodes that still stretch, let the `length` rise too: a `length` that goes from 0.7 to 1 of the full length while the `growth` goes from 0 to 1 stretches the whole path by the last 30%. With `length` alone and no `growth` everything slides up with the path, with `growth` alone nothing moves.

```
time → curve (max above 1) → stem.growth
path_info (age) → curve → branch_from_points.growth        starts when the tip of the stem passes the point
path_info (age) → math × 4 → curve → instance.size         a leaf unfolds behind the tip of the path it sits on
```

`roll` rolls up the end of a path into a flat coil, like the crozier of a fern. `roll` is the share of the path from the tip that is rolled up, `turns` how often a path turns around when all of it is rolled up. The segment whose middle lies a share `u` of the way from the start of the coil to the tip turns by `u²` of `turns * roll` turns, so the curvature grows evenly from nothing at the start of the coil to the most at the tip, and a path rolled up half as far keeps the curl of its tip. The segments keep their length. The coil lies in the plane the end of the path already bends in, a nearly straight path curls down. The share is of the path as it is now, so a growing path is curled behind its tip: `path_info (grown) → curve → roll` unrolls a frond as it grows, from the base of the coil, the tip last. Children move and turn with the spot they grow on, and with `depth` 2 they roll up themselves too, like the pinnae of a frond.

`stem` makes paths without a parent, `branch` makes every new branch with the path it grows on as parent. `join` keeps the ids as they are, only a list that clashes with one joined before it (the same list joined twice) gets new ids, parents inside it follow. A node that removes a path leaves the links of its children pointing at nothing, nodes that follow a parent must ignore a `parent_id` they can't find. A node that shortens a path changes what `parent_alpha` of its children means. A node that copies a path keeps its header, so the ids survive `gravity`, `rotate`, `noise`, `avoid`, `keep_apart`, `neighbour_sensing`, `apply_force` and `roll`.

## Force

```
[3, kind, x, y, z, radius, falloff]    all but the first two words are f32
```

A `force` output is a list of these, so a later node can combine forces. `kind` 0 is a point force: it pulls towards `x, y, z`, a negative `strength` of `apply_force` pushes away. It reaches `radius` far, `falloff` 0 keeps the full strength up to the radius and 1 fades it smoothly to nothing at the radius. `Force::sample` in `nodarium_utils` gives the push at a position, `decode_forces` and `sample_forces` read a list of them. `apply_force` bends paths with them: the base of a path stays, the segments keep their length. Paths follow the spot on their parent they grow on, so a bent stem carries its branches. `PathStructure` and `follow_parents` in `nodarium_utils::geometry` do that for any node that moves paths.

How far a segment turns towards the push at its middle is `strength * t^(0.5 + 4 * stiffness)`, where `t` is the place of the segment along its own path, 0 at the base and 1 at the tip, and `strength` is read with alpha going along the path.

## Points

```
[4, parent_id, depth, index, x, y, z, dx, dy, dz, tx, ty, tz, scale, alpha]    all but the first four words are f32
```

A `points` output is a list of these: spots where a later node can grow or place something, mostly on paths. `parent_id` is the `id` of the path the point sits on (`NO_PARENT` for a point of `spiral` or `sample_mesh`, which sits on none), `alpha` where on it (0 to 1, along its length, like `parent_alpha`), `depth` the depth of that path and `scale` its thickness there. `tangent` (`tx, ty, tz`) is the direction of the path at the point, `direction` (`dx, dy, dz`) is orthogonal to it and points away from the path: a branch grows that way, an instance sticks out that way, before their own angle tilts them. `index` is the number of the point among the points its node made on the same path, what grows on a point uses it as its own index, so its id stays the same when other points come or go. `Point`, `encode_points`, `decode_points` and `group_points_by_parent` in `nodarium_utils` read and write them.

`trunk_kink` bends the deepest paths at a few spots: everything above a kink turns by `angle`, away from the direction of the kink, and the kinks are turned around the path by `rotation` from one to the next (3.1416 bends left and right in turn). The side the kinks turn from is carried along with every bend, so kinks π (3.1416) apart stay in one plane. A kink between two points of a path adds a point there, the path keeps its length and its header. It gives the bent paths and a point on every kink, its direction points to the outer side of the bend and its tangent lies halfway between the path below and above it. Nothing grows on the deepest paths, so put it before the `branch` whose branches should follow the kinks.

`stem` makes `amount` stems from its `origin` straight up. Given `points`, like the points `sample_mesh` spreads over a substrate, every stem starts on a point instead and grows along its direction, the stems take the points in turn: with as many points as stems every stem has its own, with fewer the stems of a point grow out of one spot. The origin is not used then. The ids and the random values of the stems are the same with points as without, so a stem keeps its length when the points come or go.

To spread the stems out in a fan, two `rotate` nodes follow `stem` and one `float` a, the angle between the first and the last stem, feeds both: the first turns every stem by `a * -0.5` (a `math` multiply), the second turns stem j of n by `a * j / n` (`spread` on). So the stems fan out from `-a / 2` to `a * (n - 2) / (2 * n)`, a fan that is centred up to half a step. Both turn around the same axis, and a fan only shows in a plane the stems lie in: with `axis` x stems that grow straight up fan out in the plane of y and z, and after a `rotate x` of 1.5708 rad has laid them flat, toward +z, a fan around y spreads them in the horizontal plane, the veins of a palmate leaf. A `random` or `curve` into a makes the fan uneven, `rotate` reads its angle for every path.

`rotate` with `spread` (path j of n turned by `angle * j / n`) also spaces stems all around the plant, with 6.2832 rad around y, where the first and the last must not meet.

`keep_apart` moves whole paths without a parent sideways (in x and z), so a circle of `radius` around each of them, measured at its tip, stays clear of the others. With `lean` (hidden) the base of every path stays where it is and the path turns around it, so the tip moves aside instead, for stems that start on a substrate, which a move would lift off it. It reads `radius` with `ctx.set_path` for every path, so `path_info` length lets the room follow the size of each path. Overlapping pairs are pushed apart up to 24 times, the larger circle moves less (by the share of the other's area). Paths that grow on a moved path follow it (`follow_parents`). Because a `random` draws the same value for a path in every node that seeds it with that path, `keep_apart` and a `cap` that read the same expression first get the same radius.

`points_on_path` spreads `amount` points along every path of the `depth` deepest layers, from `lowest_point` to `highest_point` like the branches of `branch`. Each point is turned around its path by `rotation` from the one before it, and `offset_single` moves every second point up toward the next one, 1 makes pairs. Every point reads these inputs itself after `ctx.set_path` and `ctx.alpha`, so a random node gives each point its own turn. The points carry the id of their path, so `branch_from_points` and `instance_from_points` can grow on the same spots.

`spiral` makes `amount` points around one spot, for a clump of stems or a rosette of leaves that has no stem of its own to grow on. Point i of n sits at `origin` plus `height * i / (n - 1)` straight up, its tangent is up and its direction lies flat, turned by `rotation` (hidden, the golden angle 2.3998 rad by default) from the one before it, so `branch_from_points` and `instance_from_points` turn and tilt what they grow on it as `branch` and `instance` do on an upright stem: `angle` lifts a branch or a leaf from lying flat toward standing up. The first points out along -z, where `instance` puts its first leaf. Every point reads `origin`, `height` and `rotation` itself, with `alpha` from 0 at the first point to 1 at the last, so a curve of alpha makes the spiral wider or steeper from one point to the next, and `branch_from_points` and `instance_from_points` read their inputs with the same alpha: the alpha curves of a crown that `branch` or `instance` read from `lowest` to `highest` work the same. The points sit on no path (`parent_id` is `NO_PARENT`, `depth` 0, `scale` 1), so `path_info` reads nothing there and a branch on one has depth 1, like a stem; its thickness is the `thickness` of `branch_from_points` in meters, and an instance is `1.01 * size` meters long. Given `points`, like those of `sample_mesh` on a substrate, every centre gets a spiral of its own around its direction, and the origin is not used. The index of the points runs on through the spirals of all centres, so what grows on two of them gets different ids.

`random_break` breaks off some of the deepest paths at a random spot between `lowest_break` and `highest_break`, `chance` is how likely a path breaks. Whether a path breaks and where only depend on the seed and the path id, so the same paths stay broken when other paths come or go. A broken path is resampled up to the break and keeps its number of points. Nothing grows on the deepest paths, so to break a stem with its branches break it before the `branch`, which then grows on the shorter stem.

`cut` ends paths at a height: a path that rises above `height` (metres above y 0) is resampled up to where it first crosses it and keeps its number of points, a path whose base lies above is removed, and the paths that grew on a cut path above the cut are removed, the others get their `parent_alpha` rescaled. It shortens a path with `resample_up_to` of `nodarium_utils::geometry`, like `random_break`. It works on all layers by default, the hidden `depth` limits it to the deepest ones. Branches grown longer than they need to be and cut at one height end on a flat top, the corymb of a yarrow or an elder: no expression could give each branch the length that reaches a height, because a `branch` doesn't know where its parent will be bent to, and the cut happens after `gravity` and `noise` have placed everything. `height` is read once per path, so a curve of alpha tilts the top and a `random` with `once` moves it with the size of the plant.

`fill_gaps` adds paths between neighbouring paths of a fan, where they drift more than `spacing` path thicknesses apart, like the rays of a Myzel cap towards its margin. A fan is the paths one node made on one parent. Neighbours are ordered by the angle of their tips around the axis of the fan, the normal of the plane the tips spread in, and the last and the first are neighbours when the fan goes all the way round. A new path starts where the gap opens, at the same share of the length of both neighbours, and turns around the axis with them, so it keeps their distance from the axis. It sits halfway between them, moved by up to 15% of the gap by the seed, and grows from half to its full thickness over its first two radii. Every gap is filled before the gaps between the new paths, up to 1024 paths in a fan. A new path is a child of the same parent made by the same node as its neighbours, with the next free index, so `separate` keeps it with them.

`separate` takes apart paths that were joined: the first output has the paths made by the nodes that made the paths in `like`, the second the rest.

`branch_from_points` grows a branch from every point of a `points` input, for example the points of `points_on_path` or the kinks of `trunk_kink`. A branch grows along the direction of its point, `angle` tilts it toward the tangent (positive is up), its thickness starts at `thickness` times the thickness at the point and `taper` thins it to the tip. `thickness` goes up to 3, so a branch can be thicker than its path, which side veins need. The id is `PathLink::child(creator, point.parent_id, point.alpha, point.index)`, so a branch keeps its id when other points come or go, and its depth is one below the point. The points are grouped by their path and `ctx.set_path` runs once per path, so random values don't start over at every branch. A point whose path is not in `plant` still grows its branch. Like in `branch`, a branch as long as the longest path gets `resolution_curve` points, shorter ones get fewer, and the branches of a path come right before it.

`instance` takes one geometry or a list of them from a `join` node, and every instance places one of them. With `pick` random (the default) the choice is `path_id(seed, path id, instance index)`, so it only depends on the seed, the path and the number of the instance. `bias` (hidden, -1 to 1) skews it: above 0 the later geometries of the list are picked more often, below 0 the earlier ones. At 1 the last of three geometries gets about 80% of the instances and the first about 1%, at 0 all are picked equally often. With `pick` index the `index` input decides: 0 to 1 spans the list evenly, 0 is the first geometry and 1 the last, values outside are clamped. `index` and `bias` are read for every instance after `ctx.alpha` is set, like `size`, so `alpha` into `index` goes through the list from the base of the path to its tip, `path_info` with `parent position` picks by the height or age of the path, and `alpha` into `bias` makes the random pick change along the path. Instances scaled to nothing are dropped after the choice, so they don't move the picks of the others, and so are those smaller than a thousandth of the largest instance of the node, which couldn't be seen next to it. Both are measured against the instances themselves, not in meters, so a plant of a few millimeters keeps its leaves.

`instance_from_points` puts a copy of `geometry` on every point of a `points` input, for example a leaf on the points of `points_on_path` or on the kinks of `trunk_kink`. Like in `instance`, the geometry grows along its -z axis and its face looks along +y. It sticks out along the direction of the point, `angle` tilts it toward the tangent (positive toward the tip), and it faces up to the light as far as it can. The size is `(point.scale + 0.01) * size`, and the path id of every instance is `point.parent_id`, `NO_PATH` on a point of `spiral`. The points are grouped by their path, `ctx.set_path` runs once per path and `ctx.alpha` is the alpha of the point. Given a list of geometries it picks one for every instance at random, by `path_id(seed, point.parent_id, point.index)`, so the choice stays when other points come or go. `encode_instances` in `nodarium_utils::geometry` is shared with `instance`, both write their creator into the instances, so the viewport link leads from a leaf to the node that placed it, also from a leaf on no path.

`instance` turns the face of an instance (+y of its geometry, the side `y_curve` and `deform` bend it from) up to the sky as far as it can (`face` up, the default), as `instance_from_points` always does. With `face` path it turns it as if the path stood upright: toward the tip of the path and, for an instance tilted by `angle`, toward the inside of the ring, the direction in the plane of the path and the instance, at right angles to the instance. On an upright path that is the same as up. On a path that leans or nods, up turns every instance of a ring its own way, so their `y_curve` bends some toward the axis and others sideways; path keeps the ring the same all around, like the bracts and florets of a head that nods. Leaves on a horizontal branch want up, so they face the light, a head of petals path.

`umbel` grows an umbel at the tip of every path of the `layers` deepest layers (1 by default): `amount` straight rays that start at the tip, like the flower heads of wild carrot, fennel or elder. The axis of the umbel is the direction of the last segment of the path. Ray i of n sits `sqrt((i + 1) / n)` of the way out, so the rays fill the disc evenly and the last one is the outer ray, `length` long and `opening` radians from the axis. They are turned around the axis by the golden angle, plus a jitter of up to a quarter of the spacing of n even rays to either side. `shape` sets where the tips lie: 0 puts them on a flat top as high as the tip of the outer ray, so the inner rays are shorter, 1 on a dome where every ray is `length` long, values in between blend the two and negative ones make a cup. `length_variation` makes every ray up to that part shorter. The jitter and the variation only depend on `seed` and the id of the ray. With `depth` 2 every ray carries an umbellet, an umbel `umbellet_scale` times as long and as thick, so a compound umbel has `amount²` tips, depth 3 nests once more. An umbellet faces along the axis of its umbel on a flat top and along its ray on a dome. `length`, `opening`, `shape` and the other inputs are read once per umbel after `ctx.set_path` and with alpha 1, the `thickness` (absolute, in meters) with `ctx.float_along` along every ray. A ray is `PathLink::child(creator, parent, 1, i)` of the path or ray it grows on and one layer deeper, so `gravity`, `noise` and the `variants` of `to_geometry` treat it like a branch, and the rays of a path come right before it. The second output is a point at the tip of every ray of the last level, with the ray as its path, alpha 1, the ray direction as tangent and a direction that points away from the axis. `instance_from_points` with `angle` 1.5708 places a flower along the ray on each of them, an `instance` with `lowest_instance` and `highest_instance` 1 puts a ring of petals around every tip.

`to_geometry` turns paths into geometry, the step before the output: every path becomes a tube of its thickness (with the `resolution.circle` setting), and all tubes are one geometry with a material group for the paths of every node that made them, the creator of the group, so the viewer leads from a tube to its node, and the links of the paths, so it leads from a leaf on a path to the path. A geometry it gets, also one with groups like a mushroom, and instances are passed on as they are, so a leaf stays an instance. A single geometry without paths comes out unchanged. The geometry keeps the path id when all of its tubes come from the same path, otherwise it is `NO_PATH`. `max_circle_segments` and `max_points` limit the segments around and the points along each path (0 is no limit), a path with more points is resampled evenly along its length.

With `bake` on, `to_geometry` bakes everything it gets into one geometry, so a whole structure, for example an umbel with its flowers, can be placed by `instance` like a leaf: every instance becomes a transformed copy of its geometry, and geometry is added as it is. Instances scaled to nothing are left out, here and in `instance`. A baked geometry has no groups, `join` would join geometries with groups into one and the variants of an `instance` would become one. A baked part is usually small next to the plant, which is what the limits are for. Graphs from before version 17 have `bake` on.

With `variants` on, `to_geometry` bakes (also without `bake`) every stem into its own geometry and gives them as a list, like `join` does, so `instance` picks one of them for every instance. A stem is a path of the input whose parent is not in the input. The paths that grow on it (found through `parent_id`), the instances whose path id is one of these paths and the geometry made from them go into its geometry, a part that belongs to no stem goes into every geometry. Every stem draws its own random values, so a `stem` with `amount` 5 and random inputs gives five different parts. With a single stem, or none, the result is one geometry as without `variants`.

## L-system

`ramify` grows a whole branching system from one rule, the way an L-system rewrites its growing tips, without a grammar to type: the rule is put together from the inputs of the node. It starts with one tip at the origin, growing straight up, or one on every point of `points` (the points of `spiral`, `points_on_path` or `sample_mesh`), along the direction of the point. Every generation each tip adds an internode and ends it in a node, and the node makes the tips of the next generation:

```
monopodial:  A(l) → F(l) [ &(angle) A(l · ratio · (1 − dominance)) ] × laterals   A(l · ratio)   the tip grows on
sympodial:   A(l) → F(l) [ &(angle · (1 − dominance)) A(l · ratio) ] [ &(angle) A(l · ratio · (1 − dominance)) ] × (laterals − 1)   the tip ends
```

The laterals of a node are spread evenly around the axis, turned by `divergence` from those of the node before: the golden angle (2.3998 rad) and 1 lateral is a spiral, 3.1416 two ranks, 1.5708 with 2 laterals crossed pairs, 3 or more a whorl. `angle` is the branch angle between a lateral and the axis it leaves. `ratio` is how long the next internode of the leader is relative to the one the node ends, `dominance` (apical dominance) makes the other laterals shorter by its share and, in sympodial, bends the leader less: a sympodial node with `dominance` 0 forks into equal branches (dichotomous), with more one of them takes over as the leader and the line zig-zags on. A lateral shorter than a micrometre and a node with `laterals` 0 make nothing, in sympodial the tip ends there. The rule is applied `generations - 1` times, so the paths grow by about the factor `laterals + 1` (monopodial) or `laterals` (sympodial) per generation; past 8192 paths the node stops with a message instead of freezing the app.

The architectural models of Hallé and Oldeman, the forms of trees botanists tell apart, are a few settings. Monopodial with one lateral and the golden angle is a young broadleaf tree (Attims), with a whorl of 4 or 5 laterals and high dominance a tree in tiers, a pine with upright laterals (Rauh), an Araucaria with horizontal ones (Massart), and with `dominance` 1 it stays unbranched, like a palm (Corner). Sympodial with 2 equal laterals forks again and again (Schoute), with 3 it is the crown of a frangipani or a dragon tree (Leeuwenberg), with 1 lateral a chain of modules that looks like one stem (Chamberlain), and with a leader and some dominance a zig-zag trunk with branches beside it (Koriba).

Every axis is one straight path: a monopodial axis is the leader with all the internodes it adds, and its laterals grow from its nodes along it; a sympodial axis is one module, an internode whose laterals grow from its tip (`parent_alpha` 1). An axis is one layer deeper than the one it grows on, so `depth` in `path_info` is the order of an axis: 1 for the trunk, 2 for its laterals, and in sympodial one more for every generation. Its id is `PathLink::child(creator, parent, alpha, node · 16 + j)` for lateral j of the node on the parent, so it stays when other nodes make more or fewer laterals. The paths come with parents before their children, and `gravity`, `noise` and `instance` reach the layers above the deepest with their hidden `depth`; a path follows the spot it grows on when its parent bends.

The rule reads its inputs at every node, so an expression gives every node and every lateral its own: `laterals`, `ratio`, `dominance` and `divergence` once per node, `angle` for every lateral. Before an axis is rewritten the node calls `ctx.set_path_info` with it and seeds the random values with its id, so `path_info` reads the axis: `depth` its order, `index` its number on the parent, `position` its place among the laterals of the node that made it (0 to 1, so a curve of it makes the two branches of a fork unequal), `parent position` where it grows on its parent, `length` the internode the node ends. Alpha is the generation: 0 at the first node a tip makes, 1 at the last, so a curve of alpha makes the branch angle open or the internodes shrink from generation to generation, and `path_info` depth into a curve makes them differ by order. A `random` with _once per path_ gives every axis one value. `length`, the first internode, and `thickness` are read once per plant, with the first axis.

The thickness is the pipe model of Shinozaki and of Leonardo: the cross section of an axis at a spot carries everything that grows above it, so its area is proportional to the length of the paths above that spot, and `thickness` is the one of the full-grown base. Branches thin out towards their tips, a fork splits the area of its axis between its branches, which widen to the axis over their first few radii so the fork has no step, the leaves of a tip count as much as its last internode, so a grown tip ends blunt and a growing one closed, and a young plant is thinner than an old one, without an input for it.

`growth` (hidden) drives the plant through its generations: from 0 to 1 every internode grows in its own share of the time, one generation after the other, so new laterals sprout when the tip of their axis passes their node and extend while the next ones appear, and above 1 the plant only gets older (`grown` above 1, like `stem`). It is read for every axis, with alpha the generation of its first internode, and an axis never grows ahead of the one it grows on, so a `random` with _once per path_ subtracted from the time lets some axes start late without any jumping ahead of their node. As with `branch`, the plant has the same paths at every time, an axis that hasn't started is a bud, and the rule is read for the full-grown plant, so growth never changes which paths there are.

`stem` and `branch` are already an L-system of a fixed shape, one node per order: every path of a level gets the same branches, and a branch never ends its parent. `ramify` is the step back to the rule: the depth is a number instead of a chain of nodes, the length of every part follows from the one it grows on, and a tip can end and hand its growth to its laterals, which sympodial and forked plants need and `branch` can't do. The paths it gives are the same kind as theirs, so `branch`, `instance`, `gravity`, `noise`, `cut` and `to_geometry` work on them as on any plant.

## Leaves

`leaf` draws a leaf from a `shape`. `leaf_surface` grows one from its veins instead, so lobes, sinuses and teeth come from where the veins go. The veins are an ordinary path tree, made with the nodes that make branches:

`stem` (the midrib) → `rotate` x 1.5708 rad → `points_on_path` (`rotation` 3.1416, `offset_single` for pairs) → `branch_from_points` (the side veins) → `leaf_surface`

A palmate leaf, like a maple, has several main veins from one base. The `rotate` x 1.5708 rad lays the stems flat, two `rotate` y spread them in a fan, as above, and `path_info` position into a `curve` makes the middle vein the longest:

```
path_info (position) → curve (0.55 → 1 → 0.55) → stem (amount 5, length) → rotate x 1.5708 rad → rotate y (angle a * -0.5) → rotate y (angle a, spread) → points_on_path → branch_from_points → leaf_surface
float (a, 3.1416) → math (multiply by -0.5) → angle of the first rotate y, and the angle of the second
```

The leaf lies in the horizontal plane: `points_on_path` turns its points from the direction `tangent × y`, which only lies in the leaf plane for a path that lies flat, so the midrib is turned flat before the side veins grow on it. `alpha` into a `curve` into the `length` of `branch_from_points` makes the outline (long side veins in the middle, short ones at the base and tip), and its `thickness` is how far the blade reaches around a vein.

The reach of a vein is its thickness, in metres like every thickness, and `branch_from_points` sets it relative to the vein it grows on, with values above 1 for side veins whose blade reaches farther than the one of the midrib. Absolute reaches would need a second way to set the thickness of a branch, and a factor on the thickness in `leaf_surface` would scale every vein alike and still leave side veins thicker than the midrib. So the reach is the ordinary thickness of a path, any node that sets thickness shapes it, and `branch_from_points` allows a `thickness` up to 3. A palmate leaf starts from several stems fanned out from one base (`stem` with `amount` 5 and two `rotate` y). `gravity` and `noise` on the veins bend the leaf: `gravity` on the midrib arches it, on the side veins it lets the margins droop, `noise` in y makes them wavy. Only the paths go into `leaf_surface`, the veins are never extruded.

`leaf_surface` finds the frame of the leaf from the main veins, the paths whose parent is not among the veins: the base is where they start, on average, and the leaf points the way they go, seen from above. It then builds the leaf in stages, each one its own module, so a stage can be swapped without touching the others:

1. **Blade:** every vein is a round cone as wide as its thickness, and the blade is their smooth union on a grid, `resolution` cells (the `resolution.leaf` setting) across the longer side of the leaf. `smooth` is the fillet between the veins: 0 leaves a lobe or a tooth at every vein, more fills the sinuses until the margin is entire. Gaps the veins close in on every side are filled. The grid reaches a fillet beyond the veins and has at most about 1024 cells along a side, so a small leaf with a wide fillet gets larger cells instead of being cut off.
2. **Margin:** the outline of the blade, with alpha going along it from the base (0) to the tip (1) on both sides, by arc length. The `margin` input is read there and moves the margin in by that share of how far the blade reaches around the veins next to it, negative values push it out: 0.2 cuts a fifth of the reach, 1 cuts in to the vein. The reach at a point of the margin is the one of the closest point of the vein that makes the blade there, blended over a fillet and a cell between veins, so it does not jump in a sinus. A thin lobe or a tapering tip thus gets small teeth and keeps its shape, and the teeth grow with the leaf. Plain 0 leaves the outline as the veins make it. `wave` times a depth cuts teeth, a `curve` of alpha on top keeps them off the base.
3. **Mesh:** a constrained Delaunay triangulation of the margin, with the veins as chains of edges, so bending, relief and colour follow the veins. The margin is the line where the grid crosses zero, simplified along its curvature so teeth keep their points. A vein that tapers to nothing ends in a spike thinner than a cell, which the grid loses; it is rebuilt from the thickness of the vein less the share of it the margin cuts, so the tip keeps its full length. A vein that branches from another starts on a vertex of its parent's chain. Refinement then splits every triangle with an angle under 22° or longer edges than the size allows: about 2.5 cells along the margin and at the ends of the veins, growing to 8 cells in the middle of the blade. So `resolution` sets both how closely the margin follows the veins and how fine the mesh is, and a beech has about 1100 triangles at 96. The triangles run from vein to vein, and a row of points on both sides of every chain, beside each of its points and the middle of each of its edges, ends the groove of `relief` and the colour of the vein one row beside it. A bank is left out where it would come closer to the margin or another chain than it lies from its own, so where a side vein leaves the midrib the corner between them is filled from farther away.
4. **Lift:** the heights of the veins above the leaf plane, blended by distance, bend the flat mesh, and `relief` (hidden) sinks the veins into the blade, negative values raise them. Veins no higher than a ten-thousandth of the leaf, as `rotate` leaves them from rounding, count as flat.

The geometry is placed like the one of `leaf`: it grows along -z from its base at the origin and faces +y, and at `size` 1 a vein 1 m long makes a leaf as long as the one of `leaf` at size 1 (100 units). It goes into `instance` and `instance_from_points` like `leaf` does, and `set_color` reads alpha across from the midrib at x = 0. Without veins the result is an empty list, so `instance` places nothing.

### Shapes

A `shape` is one half of an outline in a box of 100 by 100, as a list `[x0, y0, x1, y1, ...]`: x goes from the margin (0) to the midrib (50), y from the tip (0) to the base (100), and the half is mirrored at x 50. The points go from the base to the tip, the first at y 100, the last at y 0:

```
x 0          x 50          y
 +-------------+-- tip ----  0
 |            /|
 |   margin  / |
 |          /  |  midrib
 |         (   |
 |          \  |
 |           \ |
 +------------\+-- base --- 100
```

`leaf` makes a slice across the leaf at every point and joins the slices, so the outline is a width at each y and has to go down from y 100 to 0 without turning back, the shape editor sorts its points by y. A lobe that points back toward the base, as on a dandelion leaf, can't be drawn with it: the veins of `leaf_surface` make such lobes, a side vein with a negative `angle` of `branch_from_points` points toward the base, and the blade follows it (see the dandelion in [PLANT_TEMPLATES.md](./PLANT_TEMPLATES.md)). Letting `leaf` take outlines that turn back would mean triangulating the outline instead of joining slices, and the slices are what `y_curve`, `x_curve` and the bulge of the midrib bend.

`mix_shape` blends two shapes point by point by a `factor`, read once without a path and with alpha 0: a `random` with `once` gives every seed its own outline between two drawn ones, like lobes that are deeper on one plant than on the next. Shapes with another number of points are both spread evenly along their outline first. Per leaf it does nothing, a shape is one outline for every instance; several leaves in a `join` are the way to differ from leaf to leaf.

### Closed bodies

`revolve` turns a shape around its midrib into a closed body: the half-width of the outline at a y is the radius of a ring there, `resolution.circle` vertices around, and both ends are closed, by a single vertex where the outline reaches the midrib and by a disc where it doesn't. It is placed like a leaf, along -z from its base at the origin, 100 long at `size` 1 and as wide as the leaf of the same shape, so `instance` places it and scales it by the thickness of the path, `set_color` reads alpha from its base to its tip and across from its axis, and `deform` bends it. `size` is read along the body like the one of `leaf`. A bud, a berry, a capsule, a seed, an achene or the receptacle of a head are an outline revolved, an `instance` with `angle` 1.5708 and `lowest_instance` and `highest_instance` 1 puts one on the tip of a path, along it. A body is closed and has no hole, so a cup or a tube that is open at one end stays sectors of a circle in a ring (see Domes and cups in PLANT_TEMPLATES.md).

### Leaf variants

`instance` places one geometry everywhere, so a plant with one leaf has the same leaf everywhere. With `variants` N, `leaf_surface` makes up to N leaves from one vein graph and gives them as a list, like `join` does, so `instance` and `instance_from_points` pick one for every instance, at random (`instance` also by `index`). The main veins, the paths whose parent is not among the veins, are dealt out to the leaves in turn, and every other vein goes with the main vein it grows from:

```
stem (amount 4, random length) → rotate x 1.5708 rad → points_on_path → branch_from_points → leaf_surface (variants 4) → instance
```

makes four leaves of one midrib each. A palmate leaf of five main veins takes `amount` 15 for three leaves of five. Dealt in turn, leaf k gets stems k, k + 3, k + 6, ... of the fan, an even fan of five every third step apart, not one side of the fan. So its veins are as evenly spread as five stems alone would be, over 12 of the 15 steps of a fan of `rotate` with `spread` (every step `a / 15`): an a of 3.927 (225°) gives three leaves of 3.1416 rad. Each leaf is built in its own frame, so the small turn between them doesn't show, but a `path_info` position reads where a stem sits in the whole fan, so a `curve` of it makes the first leaf a little longer on one side and the last on the other, and only the middle one symmetric. With fewer main veins than variants there are fewer leaves, a single leaf is one geometry as without `variants`, and `variants` 1 makes one leaf of all veins as before.

The leaves differ by what the vein graph already draws per path: `stem` seeds every stem with its id, so a `random` length differs from leaf to leaf, and `points_on_path` and `branch_from_points` call `ctx.set_path` with the midrib, so a `random` with `per_path` or a `random_int` amount there gives every leaf its own side veins. `leaf_surface` itself reads `size`, `smooth`, `relief` and `margin` for every leaf after `ctx.set_path` with its first main vein, the leaf's place among the leaves as rank: a `random` with `per_path` into the depth of the teeth makes some leaves entire and others toothed, `path_info` reads the main vein, and alpha goes from 0 at the first leaf to 1 at the last, so `alpha` into `size` makes them grow from one to the next. Each leaf is built in its own frame from its own main veins, so the stems can stand anywhere.

Building a leaf is the expensive part, placing it is cheap, so the build time grows with the number of variants and hardly with the number of instances. A `set_color` after `leaf_surface` colours every leaf of the list, and two of them joined give twice as many leaves to pick from without building more.

There is no step in the runtime that runs a part of the graph several times with other seeds or alphas: every node runs once per build, with the graph's seed. A node that wants several results from one input has to make them itself, from data that is already in the input. The paths are that data here, `to_geometry` with `variants` does the same with its stems, and a list of geometries is what `join` already gives, so no new socket type or hidden data is needed.

### Vein colour

The `color` input of `leaf_surface` colours the blade, usually the expression of a `mix_color`. It is read at every vertex the way `set_color` reads a leaf, alpha from the base to the tip and alpha across from the midrib to the margin, and in addition with **alpha vein** (the `alpha` node set to vein) and the path of the nearest vein. Alpha vein is the distance of the vertex to the nearest vein as a share of the width of its groove: 0 on the vein, 1 at the edge of the groove and beyond. The nearest vein is the one whose groove the vertex lies deepest in, and `ctx.set_path` is called with it before its vertices are read, so `path_info` (depth tells the midrib, depth 1 for a `stem`, from the side veins, depth 2) and a `random` per path read that vein. A pale midrib with fainter side veins:

```
alpha (vein) → curve (1 at 0, 0 from 0.35) ─┐
path_info (depth) → math (− 1) → curve (1 → 0.55) ─ math (×) → mix_color (factor)
mix_color (a: the blade, for example a mix of two greens by alpha across; b: pale) → leaf_surface (color)
```

The vertices on a vein are exactly on it and the row of banks beside it is at the edge of its groove, so with a curve that falls between 0 and the banks only the vertices of the chain get the colour of the vein and it fades out over one row of triangles. The line is as wide as the groove of `relief`, about 1.5 cells or 15% of the reach of the vein, whichever is more, and a finer `resolution.leaf` makes it thinner. Unconnected, the blade has no colours and keeps the viewer's material, like the leaf of `leaf`; a `set_color` after `leaf_surface` replaces the colours of the whole blade.

The other way would have been to colour the veins with `set_color` (paths carry colours, type 16) and have `leaf_surface` paint them onto the blade near them. The blade itself still needs a colour then, and the only node that could give it one, a `set_color` after `leaf_surface`, overwrites every vertex; letting `set_color` keep colours that are already there would change what it does to every coloured geometry. The vein distance can't be read by `set_color` either, because a geometry doesn't carry it, and putting it into the geometry would send data a link doesn't show. So the colour is read where the veins are known, in `leaf_surface`, with the generic `alpha`, `curve`, `path_info` and `mix_color` nodes shaping it.

### Deform

The heights of the veins arch a leaf of `leaf_surface` and let its margins droop, but they can't bend it much past 60°, roll its margins or twist it. `deform` does that to any geometry that is placed like a leaf, growing along -z from its base at the origin and facing +y: a leaf of `leaf_surface` or `leaf`, a petal, or a list of them, which it deforms one by one, like `set_color`. Its `mode` is bend, curl or twist and its `amount` is in radians, so 1.5708 is a right angle:

- **bend** arches the geometry around the x axis, positive towards its face (+y), negative away from it, a constant amount into an arc whose tip has turned by the amount. Past 1.5708 it becomes a hook.
- **curl** rolls both halves of the geometry around lines along it, a constant amount into arcs whose edges have turned by the amount: 3.1416 rolls a flat leaf into a tube, a little makes the channel of a grass blade, a negative amount on the margin alone rolls it under like the margin of sage or rosemary.
- **twist** turns the geometry around the z axis, positive turns its edge at +x up, a constant amount by the amount at the tip.

The amount is read as how fast the geometry turns where it is read, not how far it has turned, so the deformation keeps the lengths and the width of a leaf and a curve shapes where it bends. Bend and twist read it along the geometry, with alpha from 0 at its base to 1 at the vertex farthest along -z, and add up how far it turned from the base. Curl reads it at every place along and across, with alpha across from 0 on the middle (x = 0) to 1 at the edge, and adds up how far the half turned from the middle, so a `curve` of across that stays 0 up to 0.7 rolls only the outer band. The width at a place along is the widest vertex there, so a tapering leaf curls the same at every width and its tip rolls as tightly as its base. A plain `random` is drawn once per geometry, like `set_color` draws it.

```
alpha (across) → curve (0 up to 0.7, then up to 1; max -12.57) → deform (curl)    a rolled-under margin
alpha → curve (0 at the base, 1 at the tip; max 3.1416) → deform (twist)           a twist that grows towards the tip
leaf_surface → deform (curl) → deform (twist) → deform (bend) → instance
```

Each mode works in the frame of the straight geometry: curl rolls around lines along z and twist turns around the z axis. After a bend those lines are no longer the axis of the leaf, so curl and twist go before bend. Bend turns the height of a vertex with it, like a strip bent with its thickness, and curl adds it on top of the roll instead: a cupped or bent leaf is higher than the roll of a margin is wide, and turned with it, its vertices would fold over. So curl also works on a leaf of `leaf` with its own `y_curve` and `x_curve`. The normals are computed again from the faces, area weighted, on the side the old ones were turned to. Colours, the path id and the faces stay as they were. `deform` moves the vertices and adds none, so a leaf of `leaf` needs an `x_resolution` of 5 or more to roll, and an amount of 0 leaves the geometry exactly as it was.

The curve of `leaf` (`y_curve`, `x_curve`, `y_twist`) does the same for its own leaf, as radians that are read along it. `deform` is the generic way: it works on `leaf_surface` and every other geometry and its amount is shaped by the generic `alpha` and `curve` nodes, so `leaf_surface` needs no inputs for it. It has one `mode` and one `amount`, three modes in a chain where a leaf needs them, which keeps the order visible.

## Geometry

```
[1, vertex_amount, face_amount, path_id, flags, ...faces, ...positions, ...normals, ...colors?, ...groups?, n?, ...creators?, m?, ...paths?]
```

The one surface type of every node system: the leaves and stems of a plant and the body, gills and veil of a mushroom are geometry. Faces are three vertex indices each (counter-clockwise seen from outside), positions and normals three floats each. `path_id` is the `id` of the path an extruded geometry was made from (when all tubes of a `to_geometry` come from one), `-1` (`NO_PATH`) for geometry that doesn't come from a path, like a leaf or a mushroom. The viewer finds the header of the path (creator, parent) with this id. `flags` says which optional sections follow the normals (`geometry_flags` in `nodarium_utils::geometry`, `GEOMETRY_FLAGS` in `@nodarium/runtime`):

- 1, colors: an RGBA8 color for every vertex, see Colors.
- 4, groups: a material group for every vertex, a small integer. Other programs can give every group its own material, the "Groups" material of the viewer a color of its own. A geometry without groups is one group, the one of its path, so a plant is grouped by its paths.
- 2, creators (only with groups): the number `n` of groups and, for every group, the creator id of the graph node that made it (`NO_CREATOR`, `i32::MIN`, for none), so the viewport link leads from a part of the geometry to its node.
- 8, paths: after the creators, the number `m` of paths the geometry was made from and the link of each, six words as in the header of a path: id, parent id, parent alpha, creator, index and grown (`PATH_LINK_WORDS`). `to_geometry` writes the links of all paths of its input, also of buds it doesn't draw, so the viewport link still leads from an instance to the path it sits on and that path's node when only geometry reaches the output. `join` puts the links of the geometries it joins one after the other, `set_color` keeps them. `readGeometry` of `@nodarium/runtime` gives the table as `paths`, `readPathLinkTable` of `@nodarium/utils` reads it.

Plant nodes make geometry without groups, the Myzel nodes with groups and their creators. `MeshWords` reads a geometry in place, `Mesh` is one decoded and `MeshWriter` writes one straight into a result, all in `nodarium_utils::geometry`. `join` joins every geometry with groups of its inputs into one: the groups of each are numbered after those of the ones before it, they keep their creators, and a geometry without colors gets `NO_COLOR` where another has them. Paths, instances and geometry without groups stay items of the list. Before graph version 15 the Myzel surfaces were a link type of their own, `mesh`, that `join_meshes` joined and `set_mesh_color` painted.

## Instances

```
[2, vertex_amount, face_amount, instance_amount, creator, ...faces, ...positions, ...normals, ...matrices, ...path_ids, ...colors?]
```

The colors of the geometry, one per vertex, come last when it has them. One 4x4 matrix and one `path_id` per instance, the `id` of the path the instance sits on (`-1` if none). `instance` writes the path each leaf is placed on, so leaves can be picked by the part of the plant they sit on like the paths themselves. `creator` is the id of the graph node that placed them (`instance` and `instance_from_points` fill it in from their hidden `creator` input), `NO_CREATOR` for none. Nodes before it wrote 1 here, the depth of the stem. `readPathLink`, `readGeometryPathId`, `readInstancePathIds` and `readInstanceCreator` in `@nodarium/utils` read these.

## Colors

A color on a path, a geometry or instances is an RGBA8 word, sRGB with red in the lowest byte. Alpha is how much of the color shows over the viewer's material: 255 shows the color alone, 0 (`NO_COLOR`) the material, as for paths and geometry without colors, and a value in between mixes them, like the patterns `cap_pattern` lays over a cap with its `opacity`. The color nodes give opaque colors.

`leaf_surface` reads a color input the same way at every vertex of the blade, with alpha vein besides, see Leaves.

`set_color` gives the paths of the `depth` deepest levels (1, the deepest, by default) a color at every point, and every geometry in its input a color at every vertex, its groups stay. It reads the `color` input for every path after `ctx.set_path`, with alpha going along the path from 0 at its base to 1 at its tip, so a `random` with `per_path` gives every path its own color, a `path_info` into the factor of a `mix_color` one by the age of the path, and a curve of alpha a gradient along it. A plain `random` is drawn once per path, like the thickness. On a geometry alpha goes from its base, where an instance places it, to the vertex farthest from it, measured without x, the width of a leaf, so a leaf that curls up or down still ends at its tip. Alpha `across` (the `alpha` node set to across) goes from the middle of the geometry, x = 0, to its edge at the same place along, like from the midrib of a leaf to its margin, everywhere else it is 0. A leaf therefore gets its own gradient, margin or spots, and several `set_color` nodes on the same leaf, joined, let an `instance` pick a color for every leaf, at random or by its `index`, for example by `alpha` or the age of the path it sits on. A color that reads no place (no alpha and no `path_info`, like a plain color or a `mix_color` by time) is the same at every vertex: a single geometry gets it at once, the large one of a mushroom where the host copied it in, see [ABI.md](./ABI.md).

`output` and `to_geometry` give the extruded geometry of a path with colors the color of its point at every ring, the cap the color of its tip. `instance` and `instance_from_points` keep the colors of their geometry, `to_geometry` with `bake` bakes them, and the vertices of parts without colors get `NO_COLOR` there. `trunk_kink`, `random_break` and the resampling of `to_geometry` keep the colors where they were along the length of the path. Other nodes that make paths, like `branch`, `umbel` or `fill_gaps`, make them without colors, so a `set_color` goes after the node that makes a level of paths and the nodes that shape it.

`mix_color` gives a plain color when both colors and the factor are plain, and the expression otherwise, so the node that reads the color evaluates it where it uses it. The Myzel nodes read it once, without a path and with alpha 0, `set_color` at every point of a path and every vertex of a geometry. `hyphae_to_mesh` of Myzel colors the surface around the strands with the colors of their points, see Colors in [MYZEL.md](./MYZEL.md).

## Lists

Nodes can return several of these at once. They are nested with the bracket encoding from `packages/utils/src/flatTree.ts`. The `output` node's result is what the app renders.
